# Data Model: FastMCP 4 Upgrade and Connector Version Policy

**Feature**: [spec.md](spec.md) | **Plan**: [plan.md](plan.md)

This feature adds no runtime data. The entities below are the things the upgrade compares, records, and enforces. Each one names the requirement it serves.

## Tool surface

The caller-visible description of one server's tools, as returned by `list_tools`. It is the unit of before/after comparison (FR-001, FR-002, FR-006, FR-007).

| Field | Source | Comparison rule |
|---|---|---|
| `name` | tool registration, or the gateway `tool_names` mapping | MUST be identical: same set, no renames (FR-001) |
| `params[name]` | input schema `properties` | MUST be identical in name, `type`, `required`, and `default` (FR-002) |
| `inputSchema.additionalProperties` | framework | MAY change from absent to `false`. Behaviour is already rejecting (research R5). |
| `params[name].description` | docstring `Args:` (3.x+) | MAY be added. This is where `Args:` guidance moves (R6). |
| `description` | docstring leading section (3.2.4+) | MUST keep every guidance line from the baseline description, either in `description` or in a parameter description (FR-006). Section headers (`Args:`, `Returns:`, …) are not guidance lines. |
| `output_schema` | return annotation | MAY change in structure only (`$defs`/`$ref` inlining). The described shape MUST be the same (FR-004). |
| `annotations` | tool registration | MUST be identical. A `title` MAY be added (edge, R6). |

**Baselines**: [contracts/tool-surface-baseline-core.json](contracts/tool-surface-baseline-core.json) (34 tools, fastmcp 2.14.5, core `a319044`) and [contracts/tool-surface-baseline-edge.json](contracts/tool-surface-baseline-edge.json) (2 tools, fastmcp 3.0.2, edge `91f6bab`). Each holds `params` and the baseline `description`. They are not regenerated by the upgrade; changing them is a deliberate, reviewed act.

## Wire response

The payload a caller receives for one tool call (FR-003, FR-004, FR-005).

| Field | Rule |
|---|---|
| Envelope type | Pagination envelope on success, error envelope on handled failure, `isError: true` framework result on argument validation failure. Same mapping before and after (R5). |
| Error `code` | The same ADR-001 Appendix B code for the same input |
| Error `recovery_hint` | Same text |
| Absent optional fields | Omitted, never `null` (core). Edge keeps its current behaviour (FR-014). |
| Validation message text | MAY change for calls through the gateway (R5). Listed under FR-007. |

**Representative call set**: the existing `contract and integration` tier for core, and edge's nine captures (research C: success, free text, and simulated upstream 500, per tool). Upstream failures follow FR-012.

## Version policy

The platform decision that governs which framework versions connector repositories may run (FR-015 to FR-018). Defined in ADR-009. The machine-checkable part is mirrored in each repository's policy test.

| Field | Type | Initial value (proposed) |
|---|---|---|
| `framework` | string | `fastmcp` |
| `supported_range` | PEP 440 specifier | `>=3.4.7,<3.5` |
| `not_yet_supported` | list of {specifier, gate} | `>=4.0`: supported only after spec FR-020's evidence is recorded (a 4.x preview per repository; Claude Code, the claude.ai connector, Claude Desktop, and biosciences-temporal's client completing list and call against it) |
| `known_bad` | list of {specifier, reason, evidence} | `==3.4.3`: Host guard on by default, returning 421 on Horizon (edge `d4b9502`, upstream PR #4405, fixed in 3.4.4) |
| `usage_rules` | list of {rule, reason, evidence} | Never combine `namespace=` (or 2.x/3.x `prefix=`) with `tool_names` values that already carry the prefix. Every 3.x and 4.x version double-prefixes the names (`hgnc_hgnc_search_genes`); 2.x hid it. Evidence: AGE-182, core `8b112cf`/`e5e19a0`, PR #18, mount probe 2026-09-30. Enforced by the tool-surface contract test, not by version bounds. |
| `consumers` | list of repositories | `biosciences-mcp`, `biosciences-mcp-edge`, `psychology-mcp` |
| `divergence_window` | duration | Consumers may run different supported versions; none may run outside `supported_range` for longer than one release cycle after a range change (FR-015) |
| `change_procedure` | text | ADR-009 amendment, then the policy-test values updated in every consumer in the same change window, then a notice issue in each consumer repository |

**Validation rules** (each repository's policy test, no network):
1. The `fastmcp` specifier in `pyproject.toml` MUST be a subset of `supported_range`, and MUST NOT allow any `known_bad` version.
2. The `fastmcp` version in `uv.lock` MUST satisfy `supported_range` and MUST NOT match `known_bad`.
3. Every upper bound on `fastmcp` in `pyproject.toml` MUST have a reason comment on the same or the preceding line (FR-018).

## Upgrade evidence record

The per-repository record that FR-011's gate reads before a pin may be raised on `main`. It lives in this feature's `tasks.md` Convergence and verification sections and in the upgrade PR description.

| Field | Content |
|---|---|
| `repository`, `commit` | Exact head under test |
| `versions` | Resolved `fastmcp` and `mcp` |
| `tests` | Pass/fail per tier against the 2.14.5 (core) or 3.0.2 (edge) baseline; new failures listed, upstream failures marked |
| `tool_surface` | Result of the tool-surface contract test |
| `preview` | Quickstart §4 results: Host check, tool count, calls per server, sessionless call (core), rollback timing |
| `decision` | Conditional Go → Go or No-Go, with the date and who decided |

## State transitions (per repository)

```text
baseline (2.x / 3.0.x)
  → upgrade PR open (pin raised on branch; tests green; tool-surface test green)
  → preview deployed (quickstart §4 run, evidence recorded)
  → decision recorded (Go | No-Go)
      Go    → merged to main → production redeployed → policy test enforcing
      No-Go → PR closed or parked; pin stays; blocker filed
```

A repository cannot move to "merged to main" without a recorded Go (FR-011).
