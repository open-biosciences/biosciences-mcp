# ADR-009: Connector Framework Version Baseline

**Status:** Proposed
**Date:** 2026-10-01
**Version:** 0.1
**Scope:** Platform. Binds every MCP connector repository in the org (`biosciences-mcp`, `biosciences-mcp-edge`, `psychology-mcp`, and future connector repos) per the placement rule in `biosciences-program/docs/adr/README.md`. Repositories record scoped divergences in their own `docs/adr/README.md`.
**History:** v0.1 proposed with spec 015 (`specs/015-fastmcp-4-upgrade/`, contract `contracts/version-policy.md`). It is accepted as v1.0 once core and edge both run inside the range (spec 015 task T044).
**Origin:** AGE-182 and AGE-718. The repositories drifted onto different FastMCP majors because two version decisions lived only in commit messages:
- core pinned `<3.0` after 3.0.2 double-prefixed tool names (`8b112cf`, 2026-02-25);
- edge pinned `<3.4.3` after 3.4.3's Host guard returned HTTP 421 on FastMCP Cloud (`d4b9502`, 2026-07-06).

---

## 1. Context and Problem Statement

Every connector is built on FastMCP and deployed on FastMCP Cloud / Prefect Horizon. Horizon installs from each repository's `pyproject.toml`. So a dependency range is a deployment decision: whatever the range admits can run in production on the next redeploy.

On 2026-09-30, three repositories pinned the framework three different ways:

| Repository | Pin | Locked |
|---|---|---|
| `biosciences-mcp` | `>=2.14.1,<3.0` | 2.14.5 |
| `biosciences-mcp-edge` | `>=2.0,<3.4.3` (spans two majors) | 3.0.2 |
| `psychology-mcp` | `>=2.14.1,<3.0` | 2.14.7 |

Neither upper bound recorded its reason anywhere a maintainer would look. Edge was created five days after core's pin without inheriting it, and resolved the exact release that core had pinned away from. FastMCP's own release policy allows breaking changes in minor releases, so a major-only ceiling does not guarantee compatibility.

## 2. Decision

### 2.1 Supported range

**`fastmcp>=3.4.7,<3.5`** for every connector.

- **Floor 3.4.7.** It is the version verified in spec 015: tool surface, wire contract, Host behaviour, and Python clients (research R1–R13). It is also the first 3.x release with the Host guard off by default (since 3.4.4).
- **Ceiling 3.5.** This is a minor ceiling. The convention, from AGE-718, is `>=X.Y.Z,<X.(Y+1)`: an exact known-good floor and a minor ceiling. A wider range is a range change (section 2.4).

### 2.2 Not yet supported: FastMCP 4.x

4.x stays outside the range until the evidence below is recorded (spec 015 FR-020):

1. A preview deployment of each consumer on 4.x passes the same Host, tool-list, call, and rollback checks as spec 015's quickstart section 4.
2. Claude Code, the claude.ai connector, Claude Desktop, and biosciences-temporal's client each complete a list and a call against that preview.

Already known about 4.x, recorded so it isn't rediscovered (spec 015 research R1, R8, R13; PR #19 review):

- **Clients.** Python clients on `mcp` 1.26 work against a 4.0.10 server. It accepts protocol versions 2024-11-05 to 2026-07-28.
- **Tool surface.** It matches 3.4.7, except that edge gains auto-generated `title` annotations.
- **Dependencies.** 4.x moves `mcp` to 2.x.
- **Code changes.** `fastmcp.tools.tool` moved to `fastmcp.tools.base`. Unparameterized `PaginationEnvelope.create` sites log serializer warnings: 20 sites in core, 2 in edge.
- **Test coverage.** The `contract and unit` serialisation test no longer exercises 4.x's structured-content path, which goes through the return annotation's `TypeAdapter`. It must be rebased before it counts as 4.x evidence.
- **Upstream.** Issue #5213 proposes turning the Host guard back on by default.

### 2.3 Known-bad versions and usage rules

| Versions | Failure | Evidence |
|---|---|---|
| `==3.4.3` | Host guard on by default; HTTP 421 for the Horizon hostname | edge `d4b9502`; upstream PR #4405; default changed in 3.4.4 (PRs #4439, #4472) |

**Usage rule (not a version exclusion).** Never pass `namespace=` (or 2.x/3.x `prefix=`) to `mount()` together with `tool_names` values that already carry the prefix.
- Every 3.x and 4.x version double-prefixes such names (`hgnc_hgnc_search_genes`); 2.x hid the mistake.
- Evidence: AGE-182; core `8b112cf`, `e5e19a0`, and PR #18; a mount probe on 2026-09-30 against 2.14.5, 3.0.2, 3.4.7, and 4.0.10.
- Version bounds can't enforce this. Each consumer's tool-surface contract test does.

**Host-guard deployment rule.** Deploy with the framework defaults and no `FASTMCP_HTTP_*` host settings. A consumer that turns the guard on must first show, on a preview deployment, that Horizon's proxy preserves the public `Host` header. The guard does not read `X-Forwarded-Host` (upstream issue #4468).

### 2.4 Change procedure

- **New file per range change.** A range change is a new versioned file (`adr-009-vX.Y.md`), as with ADR-001 and ADR-007. An accepted file is never edited in place.
- **Tests change in the same window.** Each consumer's policy-test values are updated in the same change window as the new file, so the policy and its tests never disagree.
- **Bounds may lag.** A consumer's dependency bounds may lag the new range by at most one release cycle (section 2.5). Each consumer gets a notice issue.
- **Evidence for a raised floor.** Raising the floor requires a passing tool-surface contract test and a passing preview deployment in each consumer.

### 2.5 Divergence and consumer status

Consumers may run different versions inside the range. After a range change, a consumer may stay outside it for at most one release cycle, tracked by its notice issue.

Status at acceptance:

| Consumer | Status |
|---|---|
| `biosciences-mcp` | Inside the range: upgraded in spec 015 |
| `biosciences-mcp-edge` | Inside the range: upgraded in spec 015 |
| `psychology-mcp` | **Interim divergence** (`>=2.14.1,<3.0`, locked 2.14.7). Recorded in its own `docs/adr/README.md`; expires when its adoption issue closes (spec 015 task T043) |

Open question: whether `biosciences-memory` (`fastmcp>=2.13.3,<3`) is a connector in scope.

### 2.6 Enforcement

Each consumer carries `tests/unit/test_framework_version_policy.py`, marker `unit`, with no network access. It checks three things, and each failure message names this ADR:

1. The `fastmcp` specifier in `pyproject.toml` lies within the supported range and excludes every known-bad version.
2. The locked `fastmcp` version in `uv.lock` satisfies the range and matches no known-bad version.
3. Every upper bound on `fastmcp` has a reason comment.

A CI workflow runs `pytest -m unit` on pull requests. The policy values are copied into each consumer's test, because consumers do not import each other (edge's no-import rule).

## 3. Consequences

- **Positive:**
  - One place says which framework versions the platform supports, and why.
  - A version outside the policy fails each consumer's own CI before it can reach Horizon.
- **Negative:**
  - The policy values are duplicated in each consumer's test and must be changed together.
  - The minor ceiling means a deliberate change for every 3.x minor release.
- **Neutral:** 4.x adoption becomes a feature with named evidence, not a version bump.

## 4. Alternatives Considered

| Alternative | Rejected because |
|---|---|
| Amend ADR-004 | ADR-004 covers lifecycle, not dependency policy |
| A shared policy fetched at test time | Unit tests must not use the network |
| A shared package | Edge's no-import decision rules it out |
| Renovate-style automation | It manages bumps but can't express known-bad versions with reasons |
| A major ceiling (`<4`) | FastMCP's minor releases may break callers |
