**Why this file exists:** the patch is the derivation record — every change with its rationale

## Why this is targeted rather than a rewrite

The historical grounding in v1.5.0 is solid and should not be touched. §1 (STRING verb
taxonomy) has been *strengthened* by evidence that did not exist in January. §4.5 (CURIE
standard) holds unchanged. What has aged badly is narrow and specific:

1. **Two of the "novel contributions" were never novel** — the prior art predates v1.5.0 by
   four months.
2. **One landscape claim has moved** (TRAPI version) and one framing is now misleading (BTE
   as "the reference implementation").
3. **The document mentions MCP eleven times and never analyses it.** It grounds `search_*` /
   `get_*` in STRING's twenty-year-old REST taxonomy while never examining what MCP's own
   primitives say about that same choice. That is a gap at the centre of a document about
   interface patterns, and it is the gap that produced the current 34-tools / 0-resources
   shape without anyone deciding on it.
4. **A competitor now independently implements three of the five headline contributions.**

**Urgency note:** bump the revision *before this document is cited in any new ADR*. As
written it asserts industry-precedent grounding for things the MCP specification now
mandates outright, and it claims novelty that a reviewer can disprove in one search.

## Patch 3 — §7.1 Token Budgeting

**Rationale:** Anthropic published `response_format: concise|detailed` plus pagination,
filtering and truncation guidance on **2025-09-11 — four months before v1.5.0 claimed
novelty**. By today, `meringlab/string-mcp`, BioMCP, ToolUniverse and `smartapi-mcp` all
budget tokens; TRAPI 2.0 strips fields for the same reason.

**REPLACE** the `**Our Innovation:**` paragraph of §7.1 **WITH:**

> **Our Implementation:** Every `search_*` and `get_*` tool accepts `slim=True`, returning
> minimal fields (~20 tokens/entity vs ~115–300). This is **not a novel contribution** — it is
> the standard pattern. Anthropic's tool-design guidance (2025-09-11) prescribes a
> `response_format: concise|detailed` enum with pagination, filtering and truncation, and by
> 2026 every comparable biomedical MCP server budgets tokens. The earlier claim of novelty in
> this section was wrong and predated by four months.
>
> **What is ours:** the parameter is uniform across all 36 tools and covered by the wire
> contract tests, rather than applied per-tool at the author's discretion.
>
> **Known gap (2026-09-12):** `slim` mode drops fields *silently*. `meringlab/string-mcp`
> returns truncation metadata alongside truncated payloads (`notes`, `truncated`,
> `truncated_categories`, `omitted_categories`). That is a strictly better version of this
> pattern and is worth adopting.

## Patch 4 — §7.2 Recovery Hints

**Rationale:** Same source, same date. Anthropic's guidance explicitly says to
"prompt-engineer your error responses to clearly communicate specific and actionable
improvements." The MCP specification separately makes the mechanism normative: execution
errors are returned as a *normal result* with `isError: true` so the model can self-correct,
distinct from JSON-RPC protocol errors.

**REPLACE** the `**Prior Art:**` and `**Our Innovation:**` lines of §7.2 **WITH:**

> **Prior Art:** Anthropic's tool-design guidance (2025-09-11) already prescribes
> prompt-engineering error responses to communicate specific, actionable recovery steps. The
> MCP specification makes the transport mechanism normative: tool *execution* errors are
> returned as a normal result with `isError: true` and actionable text — not as a JSON-RPC
> protocol error — precisely so the model sees a fixable mistake rather than a broken
> connection.
>
> **Our Implementation:** `recovery_hint` is a **required, schema-typed field** on every
> `ErrorEnvelope` rather than free text, and its presence is asserted by the wire contract
> tests. The contribution is enforcement and typing, not the idea.
>
> **Open verification item:** it is not currently established whether this federation sets
> `isError: true` on the wire when returning an `ErrorEnvelope`. If it returns a *success*
> result containing an error object, the specification's self-correction path never engages
> and the recovery hint is inert. One contract assertion settles it.

## Patch 5 — §7.3 Fuzzy-to-Fact (keep, and sharpen)

**Rationale:** This section is the one genuine differentiator and currently undersells
itself. `genomoncology/biomcp` (630 stars) independently implements two-phase search→get,
identifier abstraction, progressive disclosure and next-command hints — **but accepts `BRAF`
everywhere.** ToolUniverse's protocol requires only a typed schema. The distinguishing
property is not the two phases; it is that phase 2 *refuses*.

**APPEND to §7.3:**

> **What actually distinguishes this (2026-09-12).** Two-phase resolve-then-retrieve is now
> common: `genomoncology/biomcp` implements search→get with identifier abstraction and
> progressive disclosure; `meringlab/string-mcp` — the vendor's own server — leads with
> `string_resolve_proteins`. The differentiator is **enforcement**. Phase 2 tools reject a raw
> string with `UNRESOLVED_ENTITY`, that rejection is asserted at the wire level in
> `tests/contract/`, and the refusal is part of the published contract rather than a
> convention. Comparable servers accept a bare gene symbol at the strict endpoint and resolve
> it silently, which reintroduces exactly the ambiguity the two-phase split exists to remove.
>
> State this explicitly wherever the project is described. Without it, the architecture reads
> as a smaller ToolUniverse.

## Patch 6 — §9, TRAPI compatibility

**Rationale:** TRAPI moved 1.5.0 → 1.6.0-beta → 2.0.0-beta (2026-04-02) → **2.0.0-beta2
(2026-09-10)**. Breaking changes: constraints refactored, bindings `id` → `ids` with
`attributes` removed, Knowledge Level / Agent Type promoted to required Edge properties,
`null` banned. **There is no stable 2.0.0.** Aligning an envelope against a spec that changed
twice in 2026, most recently two days ago, is premature.

**REPLACE** §9 item 1 (*"TRAPI Compatibility - Consider aligning envelope structure..."*) **WITH:**

> 1. **TRAPI Compatibility — deferred to 2.0.0 GA.** TRAPI is mid-migration: 1.5.0 →
>    1.6.0-beta → 2.0.0-beta (2026-04-02) → 2.0.0-beta2 (2026-09-10). Bindings, constraints
>    and required Edge properties have all changed during 2026 and no stable 2.0.0 exists.
>    Do not align envelopes now. Two stable ideas are worth borrowing today and cost nothing:
>    **Knowledge Level / Agent Type as first-class edge properties**, and the **no-null
>    discipline** this project already enforces via `OmitNoneModel`.

**AND REPLACE** §9 item 2 (evidence channels) **WITH:**

> 2. **Evidence Channels — now cheaper than in January.** STRING's 7-channel evidence model
>    (nscore, fscore, pscore, ascore, escore, dscore, tscore) remains essential for agent
>    reasoning about confidence. Biolink v4.4.4 (2026-08-10) added first-class STRING
>    confidence scores (PR #1772) and a StringDB-ingest association representation
>    (PR #1771), so the mapping target now exists upstream.

**AND ADD** a correction note under §9 item 3 (directionality):

> *Status 2026-09-12:* STRING v12.5 is a web-UI preview. `version-12-5.string-db.org/api/tsv/version`
> returns `12.0` and `/help/api` documents no regulatory-network endpoint, so there is nothing
> to model against yet. Revisit at the 2027 NAR paper.

## Patch 7 — NEW §4.6, The MCP Protocol Layer

**Rationale:** the document's largest gap. It analyses STRING's verb taxonomy, TRAPI,
BioThings, Biolink and the W3C CURIE specification — every layer *except the interface
protocol the entire system is built on*. MCP appears eleven times: once as "the project
follows the Model Context Protocol standard," once in the glossary, and nowhere as prior art
with its own design decisions. Insert after §4.5.

**INSERT:**

> ## 4.6 The MCP Protocol Layer
>
> MCP is not merely the transport this project happens to use; it makes its own claims about
> interface design, and those claims bear directly on the patterns above.
>
> ### Server primitives and who controls them
>
> | Primitive | Controller | Specification status |
> |---|---|---|
> | **Tools** | **Model** | Verbatim normative: *"Tools in MCP are designed to be model-controlled."* |
> | **Resources** | Application / host | Normative text is *"application-driven, with host applications determining how to incorporate context based on their needs."* "Application-**controlled**" appears only in a non-normative table — paraphrase it, do not quote it. |
> | **Prompts** | User | Surfaced as user-initiated commands; not model-invocable. |
>
> This is a command/query distinction at the protocol layer, and it maps onto §1's STRING
> verb taxonomy: the Resolve verb is inherently model-controlled (the model supplies the
> ambiguous string), while Retrieve over a stable reference corpus is the case Resources
> exist for.
>
> ### Why this federation is 36 tools and 0 resources
>
> That shape was never decided; it is the default outcome of the SDK making `@mcp.tool()` the
> path of least resistance. A deliberate assessment (2026-09-12) finds **the wholesale
> migration is correctly declined**, on four normative constraints:
>
> - `resources/read` takes only a `uri` — `slim=` has nowhere to live, and the fuzzy half of
>   Fuzzy-to-Fact cannot be expressed as a resource at all.
> - `resources/read` supports caching but **not pagination**; `PaginationEnvelope` does not map.
> - Resources are application-driven, so a registry exposed *only* as a resource is invisible
>   to the agent in most hosts.
> - Declaring the `resources` capability adds a listChanged/subscribe surface to maintain.
>
> The one genuine asymmetry worth recording, because it is easy to rediscover badly:
> **protocol-level caching applies to `server/discover`, `tools/list`, `prompts/list` and
> `resources/*` — never to `tools/call`.** A tool result cannot be client-cached no matter how
> static the underlying record is. If the 23-key cross-reference registry, the CURIE→pattern
> table or the server inventory are ever exposed as resources, caching is the reason, not
> aesthetics.
>
> ### What the specification makes normative, that this project should not re-derive
>
> - `inputSchema` **MUST** be valid JSON Schema; when a server declares `outputSchema` it
>   **MUST** conform to it, and clients **SHOULD** validate. This is the only machine-checkable
>   contract surface MCP provides.
> - Execution errors are returned as a normal result with `isError: true` and actionable text,
>   distinct from JSON-RPC protocol errors — the mechanism §7.2's recovery hints depend on.
> - **Tool annotations are explicitly untrusted**: *"clients MUST consider tool annotations to
>   be untrusted unless they come from trusted servers."* `readOnlyHint` / `destructiveHint`
>   are UI hints, never a security or policy boundary. Tiered autonomy cannot be implemented by
>   tagging tools.
>
> ### Protocol revision 2026-07-28
>
> Relevant to a read-mostly federation:
>
> - **Deprecated under SEP-2577:** Sampling, Roots, Logging, Dynamic Client Registration.
>   Earliest removal is the first revision released on or after 2027-07-28. Migration paths
>   are stated: Sampling → integrate directly with provider APIs; Roots → pass directories via
>   tool parameters or server configuration. Any design treating Sampling or Roots as
>   forward-looking is building on features being wound down.
> - **Multi Round-Trip Requests (MRTR):** `resultType: "input_required"` with an
>   `inputRequests` schema and a signed `requestState` continuation token — a server-enforced
>   human-in-the-loop gate. Normative, and correctly declined here: this federation has no
>   server-side secrets to run a signing-key lifecycle, and the mechanism has an open defect in
>   at least one major host.
> - **Elicitation** is *not* the specification's human-in-the-loop guarantee. Its approval
>   language is SHOULD-only and it is capability-gated, so a server cannot rely on it. The
>   actual statement lives on the Tools page: there **SHOULD** always be a human in the loop
>   able to deny tool invocations.

## Patch 8 — NEW §10, Competitive landscape

**Rationale:** v1.5.0 surveys databases and standards but no comparable systems, because in
January there were none worth naming. There now are, and one of them has independently built
three of this document's five headline contributions. A prior-art review that omits its
nearest competitor is not doing its job.

**INSERT before References:**

> ## 10. Comparable Systems (2026-09-12)
>
> | System | Scale | Relationship |
> |---|---|---|
> | **BioMCP** (`genomoncology/biomcp`, 630★) | Overlapping sources | **Nearest competitor.** Independently implements two-phase search→get, identifier abstraction, progressive disclosure and next-command hints. Accepts bare symbols at strict endpoints. |
> | **ToolUniverse** (Harvard/Zitnik, arXiv 2509.23426, 1,680★) | 1,000–2,700+ tools *(counts disagree across sources)* | The scale reference, with its own AI-Tool Interaction Protocol. |
> | **string-mcp** (`meringlab`, `mcp.string-db.org`) | STRING only | **Vendor-operated.** First tool is `string_resolve_proteins` — independent confirmation of §1's reading. Makes this federation's STRING server a third-party duplicate. |
> | **BioContextAI Registry** (Nat Biotechnol 2025, `s41587-025-02900-9`) | 71 servers | The field's discovery layer, CI-enforced `meta.yaml`. **biosciences-mcp is not listed and clears the bar today.** |
> | **MCPmed** (Brief Bioinform, 2026-02-23) | — | A published *call* for EDAM/Bioschemas-tagged tool schemas, not an adopted convention — reference repos have 1–12 stars and mostly stopped in July 2025. Cite; do not adopt. |
>
> **Consequences for this document's claims.** Three of the five §7 contributions exist in a
> 630-star competitor. The remaining differentiator is narrow, real and defensible: the
> **enforced** strict phase (§7.3) and the 23-key `cross_references` registry (§7.4). Compete
> on depth of contract, not breadth of tool surface — 36 tools against 1,000+ is a losing
> frame, and was never the axis.
>
> **One open decision this forces.** With `mcp.string-db.org` live and vendor-operated, the
> STRING server here duplicates an official upstream. That is a deliberate build-vs-defer call,
> not a default. No other upstream ships an official MCP server — per EMBL (2025-12-02), MCP is
> "something we are exploring across the EMBL-EBI services" — so there is no wave about to
> obsolete the rest of the federation.
